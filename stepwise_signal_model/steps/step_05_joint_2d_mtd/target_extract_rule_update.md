# 第5步目标提取参数修改说明

## 1. 当前主链路没有变，变的是“目标后筛选规则”

当前第 5 步的主链路仍然是导师确认后的“局部单目标验证链路”：

1. 假定已经扫描到目标附近
2. 选取目标附近的局部三波束
3. 由于方位三波束和俯仰三波束共享中心束，所以实际形成 `5` 个唯一局部波束
4. 做局部波束形成，得到 `beamCube = 5 x R x P`
5. 做 MTD，得到 `rdCube = 5 x R x D`
6. 只在中心波束的 `1 x R x D` 上做 CFAR
7. 对 raw CFAR 检测点做 RD 聚类
8. 对聚类结果做目标后筛选
9. 对最终保留的最强目标做三波束比幅测角

这次真正修改的是第 8 步，也就是“聚类后的目标后筛选规则”。

## 2. 规则是怎么一步一步改过来的

### 2.1 最开始的单目标手调版本

最开始的版本更接近“为了当前单目标验证先把结果压成 1 个目标”的做法：

- `count >= 2`
- `metricSum >= 1000`

这个版本能在当前场景里工作，但问题是：

1. `1000` 本质上是手调常数
2. 它非常依赖当前仿真幅度、噪声和 CFAR 输出
3. 换一组参数后，这个常数不一定仍然合适
4. 它更像“当前实验有效”，不太像“可以解释给导师听的规则”

### 2.2 第一步普适化：先改 `metricSum`

后面先做的第一步修改是：

- 保留 `count >= Nmin`
- 把固定 `metricSum >= 1000` 改成
  `metricSum >= max(Tabs, Tbg)`

其中：

- `Tabs` 是绝对下限
- `Tbg` 是背景簇统计构造出来的自适应门限

当前代码里：

- `Nmin = 2`
- `Tabs = 50`
- `Tbg = median(backgroundMetricSum) + Kmad * MAD(backgroundMetricSum)`
- `Kmad = 8`

这样做的原因是：

1. 当前主目标和杂散簇在 `metricSum` 上差异最大
2. 所以最先值得普适化的是 `metricSum`
3. 这一步改动小，但能先把“固定常数门限”升级成“数据驱动门限”

### 2.3 为什么又把 `doppSpan` 规则删掉了

中间我们曾经尝试过补一条第二步几何规则，也就是限制簇在 Doppler 维上的跨度。

但这条规则当前又被删掉了，原因很直接：

1. 它在当前场景里的区分力不够稳定
2. 主目标簇和部分杂散簇在 `doppSpan` 上仍然有重叠
3. 如果把它作为硬筛选条件，就有误伤主目标的风险
4. 对当前单目标局部验证链路来说，它会让规则变复杂，但收益不够明确

所以当前采取的策略是：

- 不用一个区分力还不够稳定的条件去做硬筛选
- 先把规则收敛回更清楚、更可解释的版本

## 3. 当前完整的参数逻辑

当前后筛选只保留一层显式规则：

1. `count >= Nmin`
2. `metricSum >= max(Tabs, Tbg)`

也就是说，当前只依赖：

- 最小簇大小
- `metricSum` 绝对下限
- `metricSum` 自适应背景门限

### 3.1 最小簇大小

先要求：

- `count >= 2`

作用：

- 去掉明显孤立的单点虚警

### 3.2 `metricSum` 门限

再要求：

- `metricSum >= max(Tabs, Tbg)`

其中：

- `Tabs = 50`
- `Tbg = median(backgroundMetricSum) + 8 * MAD(backgroundMetricSum)`

背景簇的构造方式是：

1. 先取满足 `count >= 2` 的簇
2. 按 `metricSum` 从大到小排序
3. 排除最强的前 `TopK = 1` 个簇
4. 用剩余簇作为背景样本

作用：

- 让主目标簇不过度主导背景统计

## 4. 当前参数及含义

### 4.1 `cfg.cfar.targetExtractMinClusterSize = 2`

含义：

- 最少需要 `2` 个 raw CFAR 点形成一个簇

### 4.2 `cfg.cfar.targetExtractMinMetricSum = 50`

含义：

- `metricSum` 的绝对下限 `Tabs`

作用：

- 在背景样本不足时兜底

### 4.3 `cfg.cfar.targetExtractAdaptiveMinClusterCount = 3`

含义：

- 至少要有 `3` 个背景簇样本，才启用自适应门限

### 4.4 `cfg.cfar.targetExtractAdaptiveExcludeTopK = 1`

含义：

- 背景统计前先排除最强的 `1` 个簇

### 4.5 `cfg.cfar.targetExtractAdaptiveMadScale = 8`

含义：

- `Tbg = median + 8 * MAD`

## 5. 为什么要从“单目标手调规则”过渡到“更普适规则”

这里要区分两件事。

### 5.1 当前主链路仍然是单目标局部验证

第 5 步现在还不是完整工程版多目标全域搜索，而是：

- 已经假定扫描到目标附近
- 只取局部波束
- 只在中心波束上做检测

所以它的定位仍然是：

- 验证局部处理链路能不能跑通

### 5.2 但后筛选规则不能一直停在“当前场景手调”

即使主链路还是单目标验证，后筛选规则也不能永远停在：

- “为了这一次结果，只写一个经验常数”

因为这样会带来两个问题：

1. 一旦仿真参数变了，原有门限不一定还有效
2. 后面如果继续向更复杂场景扩展，每一步都会被这些手调常数拖住

所以当前的改造思路是：

- 主链路先不扩张
- 但把后筛选规则逐步从“单目标手调常数”升级为“更可解释的显式规则”

## 6. 现在这套规则的定位是什么

当前这套规则的定位是：

- “从单目标手调版走向更普适版的简化版本”

它比原来更好，因为：

1. 不再只依赖一个固定 `metricSum` 常数
2. 有了背景簇驱动的自适应门限
3. 规则数量仍然保持较少，便于解释和调试

但它还不是最终完整工程版目标提取规则，因为它还没有覆盖这些内容：

1. `rangeSpan`
2. `bestMetric / metricSum`
3. 中心一致性
4. 波束一致性
5. 多目标场景下的目标列表管理

所以更准确地说，当前版本是：

- “第一步普适化后的简化规则”

而不是：

- “最终版目标提取器”

## 7. 代码层面现在保留了什么

### 7.1 `bf_joint_2d.m`

当前保留的目标提取辅助信息主要有：

- `targetExtractInfo.metricSumRule`
- `targetExtractInfo.metricSumAdaptiveRule`
- `targetExtractInfo.metricSumFinalThreshold`
- `targetExtractInfo.keepMaskStage1`
- `targetExtractInfo.keepMaskFinal`

这样做的好处是：

- 既能解释门限来源
- 又不会把规则链拉得太长

### 7.2 `demo_joint_2d_mtd.m`

终端输出现在只打印：

- 当前 `metricSum` 最终门限
- `Tabs`
- `Tbg`

不再打印 `doppSpan` 上限，避免把当前已经删除的规则继续混在输出里。

## 8. 后面如果还要继续补规则，建议怎么做

如果后面还要继续推进，我建议仍然保持“每次只加一条规则”的节奏：

1. 先观察当前 `count + metricSum` 的结果是否稳定
2. 如果确实不够，再补下一条规则
3. 新规则只有在“明显提升区分力”时再留下

这样做的好处是：

1. 每条规则都能单独解释
2. 每个参数的作用都能单独验证
3. 不会让当前单目标局部验证链路过早变得过于复杂

## 9. 当前保留的独立测试脚本与已观察到的问题

为了不把还没验证充分的规则直接迁回第 5 步主链路，当前专门保留了一个独立测试脚本：

- `test_joint_2d_seed_stability.m`

它的定位不是“正式处理链路”，而是：

- 在不改主函数 `bf_joint_2d.m` 的前提下
- 对不同噪声随机种子下的目标提取稳定性做快速扫描
- 顺带验证某些额外抑制规则是否值得进入主链路

### 9.1 这个测试脚本发现了什么问题

在当前单目标局部验证场景下，对 `seed = 1:10` 做扫描后，观察到了一个比较稳定的现象：

1. 主目标的三波束比幅测角结果本身比较稳定
2. 但目标提取阶段并不总是只保留 1 个目标
3. 有一半左右的随机种子会额外保留一个很弱的第二簇

进一步观察这个第二簇，可以总结为：

1. 它和主目标处在几乎相同的距离单元
2. 它通常只比主目标偏移约 `4` 个 Doppler bin
3. 它的 `metricSum` 和 `bestMetric` 都明显弱于主目标
4. 从现象上更像主目标泄漏/旁瓣带来的次簇，而不像一个真实独立目标

也就是说，当前主链路里的：

- `count >= Nmin`
- `metricSum >= max(Tabs, Tbg)`

虽然已经比最早的手调常数更合理，但在这个局部单目标场景里，仍然会把一类“贴着主目标、但能量极弱的次簇”一起保留下来。

### 9.2 测试脚本里尝试了什么验证性方案

在测试脚本里，额外尝试了一条“只针对当前现象”的验证性抑制规则。

它不是直接改主链路，而是在主链路输出之后，单独对保留下来的目标列表做一次附加判断：

以最强目标为参考，如果某个次目标同时满足：

1. `rangeGap <= 1 bin`
2. `doppGap <= 4 bin`
3. `metricSumRatio <= 1e-3`
4. `bestMetricRatio <= 1e-3`

则把它标记为“当前主目标附近的极弱次簇”，在测试脚本里做抑制。

这里的含义是：

- 距离上几乎和主目标重合
- Doppler 上只是在主目标附近偏几格
- 总能量远小于主目标
- 峰值强度也远小于主目标

### 9.3 这个验证性方案的结果

当前已经观察到的测试结果是：

1. 原始主链路规则下，`10` 组随机种子中约有 `5` 组最终保留 `1` 个目标
2. 加入上述验证性抑制后，`10` 组随机种子都保留为 `1` 个目标
3. 主目标的距离、速度和三波束比幅测角结果并没有被破坏
4. 三波束比幅测角也没有因为这条验证性抑制而退回到回退分支

这说明：

- 这条附加规则对“当前这个第二簇现象”是有效的
- 它确实能把当前单目标局部场景里那类稳定出现的弱次簇压掉

### 9.4 为什么暂时不迁移回第 5 步主链路

尽管这条方案在测试脚本里是有效的，但当前仍然不建议直接并入第 5 步主链路，原因是：

1. 它是围绕“当前这个第二簇现象”写出来的针对性规则
2. 其中 `doppGap <= 4`、`1e-3` 这类阈值还没有经过更广泛场景验证
3. 它更适合作为“可能的后续探究方向”，而不是马上当作正式主规则

因此当前的处理原则是：

- 主链路继续保持现在的简化版后筛选规则
- 独立测试脚本保留下来，专门用于后续验证这类附加抑制思路

### 9.5 当前文档对这部分内容的最终定位

这部分内容现在的定位应当理解为：

- “一个已经观察到的稳定现象”
- “一个在独立测试脚本中验证有效的候选解决方案”
- “后续可继续扩展、但暂未并入主链路的探索方向”

而不应理解为：

- “当前第 5 步正式主链路已经采用的目标提取规则”
