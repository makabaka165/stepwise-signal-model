# Step 05 当前版本流程与维度说明

## 0. 当前定位与关键假设

当前第 5 步已经切换为“仿真阶段局部单目标链路”，不再走之前那个全 `3201` 联合波束的工程化全域扫描。

这里需要特别说明：

1. 当前不是“先在完整波束网格上搜索目标，再做检测”的全域流程。
2. 为了降低计算量，当前仿真阶段先假定系统已经扫到目标附近，并且已经拿到了目标附近的局部三波束。
3. 代码实现时，由于方位三波束和俯仰三波束共享同一个中心束，所以实际统一形成的是 `5` 个唯一局部波束，而不是 `6` 个。
4. 后续的 MTD、中心束 CFAR、目标提取和三波束比幅测角，都是直接在这组局部波束上完成的。
5. 因此当前第 5 步验证的是“局部处理链路是否正确”，而不是“全域搜索流程是否完整”。

当前思路可以概括为：

1. 先按当前扇区中心选择工作子阵。
2. 在当前工作子阵上生成方位轴和俯仰轴的一维波束中心。
3. 仿真阶段直接用“离 `cfg.tgt.az` / `cfg.tgt.el` 最近的波束中心”近似当前已经扫描到的局部中心束。
4. 围绕该中心束，构造方位三波束和俯仰三波束。
5. 由于两个三波束共享中心束，所以实际一共形成 `5` 个唯一局部波束。
6. 对这 `5` 个局部波束统一做波束形成和 MTD。
7. CFAR 只放在中心波束的 RD 图上。
8. 中心波束 CFAR 检出多个检测单元后，当前直接对 raw CFAR 检测点做 RD 聚类，再做目标后筛选。
9. 当前后筛选只保留 `count + metricSum` 这一层显式规则。
10. 最终三波束比幅测角只对“后筛选保留的最强目标代表点”执行。

## 1. 记号

- `N`：当前工作子阵的有效阵元数
- `R`：距离单元数
- `P`：脉冲数
- `D`：多普勒单元数
- `B_local`：当前局部唯一波束数，这里固定为 `5`

在当前默认配置下：

- `Naz = 192`
- `Nel = 32`
- `sectorHalf = 60 deg`
- `subNaz = 2 * floor(60 / 1.875) + 1 = 65`
- `N = 65 * 32 = 2080`
- `R = 3000`
- `P = 32`
- `D = 32`

因此当前第 5 步的核心维度链路是：

- `pcCube = 2080 x 3000 x 32`
- `beamCube = 5 x 3000 x 32`
- `rdCube = 5 x 3000 x 32`
- `center beam CFAR input = 1 x 3000 x 32`

## 2. 每一步输入输出维度

### 2.1 阵元级脉压输出

输入到第 5 步主函数的是：

- `pcCube(element, range, pulse)`
- 维度为 `N x R x P = 2080 x 3000 x 32`

含义是：

- 第 1 维 `2080`：工作子阵阵元编号
- 第 2 维 `3000`：距离单元
- 第 3 维 `32`：慢时间脉冲编号

这一层还没有形成波束。

### 2.2 单个波束先得到 `R x 32`

对任意一个候选波束，设其接收权向量为：

- `w : N x 1`

固定某个脉冲时：

- `pcCube(:, :, p) : N x R`
- `w^H : 1 x N`

则有：

- `w^H * pcCube(:, :, p) : 1 x R`

对全部 `32` 个脉冲都做完并堆叠后，得到：

- `beamMat : R x P = 3000 x 32`

这正对应导师提到的那句：

- “一个波束先得到 `R x 32`”

### 2.3 当前不是全域联合波束，而是局部 `5` 波束

当前版本不是构造完整二维联合波束网格，而是只构造目标附近的局部波束：

- 方位左束
- 中心束
- 方位右束
- 俯仰下束
- 俯仰上束

其中：

- 方位三波束是 `[azLeft, center, azRight]`
- 俯仰三波束是 `[elDown, center, elUp]`
- 中心束被两组共享

所以波束形成之后得到：

- `beamCube(localBeam, range, pulse)`
- 维度为 `5 x 3000 x 32`

这就是当前第 5 步用来降低复杂度的关键。

### 2.4 两组三波束的视角

虽然总共只形成了 `5` 个唯一波束，但为了后续三波束测角，可以把它看成两组三波束：

- 方位组：`[azLeft, center, azRight]`
- 俯仰组：`[elDown, center, elUp]`

因此从 `beamCube(5, R, P)` 中可以直接抽出：

- `azGroup = 3 x R x P`
- `elGroup = 3 x R x P`

注意这里没有重复形成中心束，只是索引复用。

### 2.5 MTD 后变成 `5 x R x D`

对 `beamCube(5, R, P)` 沿脉冲维做 MTD：

- 输入：`5 x 3000 x 32`
- 输出：`rdCube(localBeam, range, doppler)`
- 维度：`5 x 3000 x 32`

数值上第三维仍然是 `32`，但物理意义已经从脉冲维 `P` 变成了多普勒维 `D`。

同样地，也可以抽出：

- `azGroup.rdCube = 3 x 3000 x 32`
- `elGroup.rdCube = 3 x 3000 x 32`

## 3. CFAR 放在什么位置

当前版本采用的是：

1. 先做局部 `5` 波束波束形成
2. 再做 MTD
3. 然后只对中心波束的 RD 图做 CFAR

也就是说：

- CFAR 输入不是 `5 x R x D`
- 而是中心波束切片 `1 x R x D`

在代码里，中心波束就是局部波束编号 `2`。

所以 CFAR 实际检测的是：

- 中心波束对应 RD 图上的检测单元

其输出不是目标列表，而是检测单元列表：

- `rangeIdx`
- `dopplerIdx`
- `metric`
- 以及映射后的 `range`
- `velocity`

## 4. 当前目标提取链路

当前目标提取不是完整工程版多目标提取，而是当前局部验证版本的简化链路：

`raw CFAR -> RD 聚类 -> 目标后筛选 -> 最强目标代表点`

### 4.1 raw CFAR

中心波束 CFAR 的输出是若干个检测单元点：

- 它们只是“通过门限的 RD 单元”
- 还不等于最终目标

### 4.2 RD 聚类

当前代码直接对 raw CFAR 检测点做 RD 聚类。

聚类不是用连通传播，而是“按强点做种子窗口归并”：

1. 按检测强度从强到弱处理
2. 用当前强点作为种子
3. 吸收种子附近满足 `rangeTol / doppTol` 的检测点
4. 不做传递式链式扩张

每个簇至少记录：

- `count`
- `bestMetric`
- `metricSum`
- `rangeIdxMin / rangeIdxMax`
- `doppIdxMin / doppIdxMax`
- `seedRangeIdx / seedDoppIdx`

### 4.3 当前后筛选规则

当前后筛选已经简化为一层显式规则：

- `count >= Nmin`
- `metricSum >= max(Tabs, Tbg)`

其中：

- `Tabs` 是绝对门限
- `Tbg` 是从背景簇统计构造的自适应门限

当前保留这套规则的原因是：

1. 它比固定常数门限更普适
2. 它比再叠加额外几何条件更稳定
3. 当前 `doppSpan` 这类几何约束区分力还不够稳定，容易让规则变复杂

### 4.4 最终只保留一个代表目标做精测角

当前第 5 步仍然是局部单目标验证接口，所以：

1. 后筛选后得到若干保留目标
2. 从中选最强的一个作为 `finalDetection`
3. 三波束比幅测角只对这个 `finalDetection` 执行

因此当前版本最终不是输出完整多目标列表接口，而是输出：

- “当前局部链路下的最强目标结果”

## 5. 当前第 5 步的输出

当前版本的输出可以分成 4 部分。

### 5.1 波束选择结果

- 当前工作子阵规模
- 方位波束轴 / 俯仰波束轴
- 选中的中心束
- 方位三波束
- 俯仰三波束

### 5.2 中心束检测结果

当前代码会同时保留：

- `cfarRaw`
- `clustersRaw`
- `candidateTargets`
- `targets`

其中含义分别是：

- `cfarRaw`：原始 CFAR 检测单元
- `clustersRaw`：聚类结果
- `candidateTargets`：每个聚类簇挑出的代表点
- `targets`：经过后筛选后真正保留的目标代表点

### 5.3 目标提取辅助信息

当前还会输出：

- `targetExtractInfo`

其中会记录：

- `metricSum` 相关门限
- 背景簇统计
- `keepMaskStage1`
- `keepMaskFinal`

这样就可以直接解释：

- 某个簇为什么被保留
- 某个簇为什么被过滤

### 5.4 最强目标的三波束比幅测角结果

如果后筛选保留了目标，则：

1. 取最强目标对应的 `(rangeIdx, dopplerIdx)`
2. 在该单元上读取方位三波束响应
3. 在该单元上读取俯仰三波束响应
4. 分别做三波束比幅测角

最终输出：

- `bestAz`
- `bestEl`
- `bestRange`
- `bestVel`

## 6. 三波束比幅测角在当前版本中的位置

当前版本里，三波束比幅测角不是用来“找目标”的，而是用来“精化角度”的。

顺序是：

1. 中心波束 CFAR 先找到检测单元
2. 对 raw CFAR 检测点做 RD 聚类
3. 对聚类结果做目标后筛选
4. 从保留目标里取最强的一个
5. 在这个检测单元上读取局部三波束响应
6. 用左右差和比

   `rho = (A_right - A_left) / (A_right + A_left + eps)`

   做角度反演

因此它回答的是：

- “这个已经检测并提取出来的目标，它的精细角度是多少”

而不是：

- “整个扇区里有哪些目标”

## 7. 当前版本与之前工程化思路的区别

之前工程化思路是：

- 全二维联合波束全域扫描
- 全域 MTD
- 全域 CFAR
- 检测后再做目标提取和聚类

当前版本不是这条路，而是：

- 已经假定当前扫描到了目标附近
- 只取目标附近的局部三波束
- 因共享中心束而实际形成 `5` 个唯一局部波束
- 只在中心波束上做 CFAR
- 只在中心波束 RD 平面内做聚类和目标后筛选
- 只对最强目标代表点做三波束精测角

所以当前版本的定位是：

- 仿真阶段
- 局部单目标验证链路
- 重点验证“局部三波束/五波束 + MTD + 中心波束 CFAR + 目标提取 + 比幅测角”是否合理

而不是：

- 完整工程版多目标全域搜索检测链路

## 8. 当前版本最核心的维度总结

一句话概括当前第 5 步的维度：

- `pcCube = N x R x P = 2080 x 3000 x 32`
- 单个波束输出 `R x P = 3000 x 32`
- 局部 `5` 波束输出 `5 x R x P = 5 x 3000 x 32`
- MTD 后得到 `5 x R x D = 5 x 3000 x 32`
- 中心波束 CFAR 输入是 `1 x R x D = 1 x 3000 x 32`
- 方位精测角读取 `3 x 1` 响应
- 俯仰精测角读取 `3 x 1` 响应

这就是当前代码真实对应的处理链路和维度含义。

## 9. 当前额外保留的测试脚本，不属于主链路

除了上面的正式主链路外，当前还额外保留了一个独立测试脚本：

- `test_joint_2d_seed_stability.m`

它的作用不是替代第 5 步主流程，而是：

1. 在不同随机种子下重复跑当前局部单目标链路
2. 观察 raw CFAR 聚类和目标后筛选的稳定性
3. 验证某些“可能有用但暂未正式采用”的附加抑制规则

这里要特别区分清楚：

### 9.1 主链路当前仍然是什么

主链路仍然是本文前面写的这条：

- `pcCube -> 5 个局部波束 -> MTD -> 中心束 CFAR -> RD 聚类 -> 后筛选 -> 最强目标三波束比幅测角`

也就是说，主链路当前并没有额外增加“二次抑制步骤”。

### 9.2 测试脚本里多做了什么

测试脚本是在主链路输出结果之后，额外观察：

- 是否存在一个和主目标距离几乎相同
- Doppler 上只偏几格
- 但能量和峰值都远弱于主目标

的第二簇。

如果出现这种情况，测试脚本里会把它当作“候选弱次簇”做验证性抑制。

### 9.3 为什么这部分暂时单独保留

原因是：

1. 它当前更像“针对已观察现象的探索性处理”
2. 还不是已经确认普适的正式主规则
3. 单独保留成测试脚本，后续更便于比较“加规则前后”的差异

因此当前第 5 步的正确理解应该是：

- 主链路负责局部单目标处理验证
- 独立测试脚本负责稳定性扫描和候选规则探究
